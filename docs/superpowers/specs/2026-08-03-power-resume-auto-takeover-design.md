# 睡眠恢复与自动接管设计

## 目标

修复 FanControl Pro 在 Windows 睡眠恢复后永久显示“接管状态异常”的问题，并让用户可以选择在开机及睡眠恢复的只读自检完成后自动恢复风扇接管。

## 已确认根因

- `CCore::Run()` 在读取配置后无条件将 `m_config.TakeOver` 置为 `FALSE`，因此自启动后不会恢复接管。
- 程序没有处理 Windows 电源挂起或恢复通知。睡眠恢复期间若 EC 连续返回无效温度，`SensorHealthPolicy` 会进入永久故障状态；`SetUserTakeoverAuthorized()` 只重置接管验证，不会重置传感器健康状态，导致重新勾选接管无法恢复。

## 行为设计

### 持久化授权

新增 `AutoTakeoverAfterCheck` 配置项，默认关闭。用户主动开启后，程序保存此偏好；该偏好不是立即写 EC 的授权。

启动时保留配置中的自动接管偏好，但始终先进入只读自检。三次连续有效的 CPU/GPU 温度采样完成后，只有 `AutoTakeoverAfterCheck` 为真时才申请接管。关闭该选项时，程序保持 BIOS 控制并允许用户手动接管。

### 电源恢复状态机

界面对 `WM_POWERBROADCAST` 处理如下：

1. 收到挂起通知时，仅请求核心停止后续写入；不在 UI 线程调用任何 EC 接口。
2. 收到恢复通知时，核心线程执行一次恢复会话重置：清空目标占空比、接管回读计数、传感器健康失败计数及启动自检计数，取消临时强冷，并进入 `SelfChecking`。
3. 恢复会话期间不允许写 EC；UI 显示“睡眠恢复后正在重新自检，BIOS 风扇控制保持启用”。
4. 三次只读温度采样通过后，若用户此前启用了自动接管，核心才重新请求接管；否则保持 BIOS 控制。
5. 自检失败时保持仅监控和 BIOS 控制，不尝试自动重试写入；用户可在读数恢复正常后手动请求接管，或再次经历恢复流程。

`ResetFan()` 仅由核心线程执行。若睡眠前程序确实曾写入 EC，恢复后的第一次核心循环可请求归还 BIOS；该写入在会话重置前后均不发生自动接管写入。

### 可恢复故障

手动关闭再开启接管时，清空接管验证和传感器健康状态，并重新进入只读自检，而不是直接在可能过期的 EC 会话上写入。这样既能恢复使用，也不会把未知传感器状态当作安全状态。

### 可观测性

诊断日志新增中文事件：收到挂起、收到恢复、开始恢复自检、恢复自检成功、自动接管请求、恢复自检失败、用户手动重新接管。诊断报告继续保留最近 200 行，因此可定位下次异常发生在哪个阶段。

## 接口边界

- 新增独立的 `PowerResumePolicy`，只负责电源恢复会话状态与“是否应在自检后自动申请接管”的决定，不依赖 MFC、DLL 或 EC。
- `CCore` 公开线程安全的电源事件请求入口；UI 只发送事件，不改变 EC 状态。
- `StartupSelfCheckPolicy` 保持只读；任何 EC 写入均经过现有 `CanWriteFans()`，且只有核心状态为 `CoreReady`、自检通过、用户授权有效时才可发生。

## 测试与验证

- 独立策略测试：恢复会话先禁止写入、三次有效采样后才允许自动申请、未启用自动接管则仍保持 BIOS 控制、手动重试会重新自检。
- 配置持久化测试：新字段默认关闭、读写后保持、旧 V4 配置可无损迁移。
- 回归现有启动自检、传感器故障、接管验证、配置恢复及诊断报告测试。
- 构建 `Debug|Win32` 与 `Release|Win32`，并在真实电脑上验证启动、接管、睡眠恢复、关闭自动接管四个场景。开发验证期间不自动执行真实 EC 接管。
